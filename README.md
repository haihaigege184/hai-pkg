# hai 本地包

> 面向 **影视 / OK影视 / TVBox(FongMi 系)** 的自维护接口包。
> 站点域名一直漂移，这个包会**自己把失效域名换掉**，让电视机长期不用管。

## 一、直接在电视机上用（推荐）

播放器里「点播接口 / 配置地址」填下面任意一条：

| 场景 | 地址 |
| --- | --- |
| **局域网（同一 WiFi，最快，推荐）** | `http://10.0.0.11:8099/hai/jsm.json` |
| 局域网 · 同目录布局（等同原始 zip 解压目录） | `http://10.0.0.11:8099/jsm.json` |
| **公网①（Cloudflare 隧道，实测最快）** | `https://hai.haihaigege.dpdns.org/hai/jsm.json` |
| 公网②（自建 gost 穿透，备用） | `https://hai.gl-hk1.gost.de5.net/hai/jsm.json` |

填完保存即可，不需要下载 zip、不需要解压、不需要手动上传 `js` / `lib`。

> **实测（2026-10-23，服务器自测，curl 连打 3 轮取中位数）**：
>
> | 入口 | `jsm.json` 耗时 | 备注 |
> | --- | --- | --- |
> | 局域网 `10.0.0.11:8099` | **18 ms** | 最快，推荐 |
> | 公网 Cloudflare `hai.haihaigege.dpdns.org` | **约 0.9 s** | 公网首选 |
> | 公网 gost `pg.gl-hk1.gost.de5.net` | 约 1.8 s | 会抖（实测出现过 4.3 s） |
> | 公网 gost `hai.gl-hk1.gost.de5.net` | 约 2.2 s | 最慢且最抖 |
>
> 所以**公网首选 Cloudflare，不是 gost**（README 旧版写反了）。
>
> 维护页有「入口测速」面板（`/live` → 配置地址卡片），可随时复测；
> 也支持让中枢**定时测速并自动择优**渲染口径（见下文「入口测速与渲染口径」）。
> **注意**：电视端填的**配置地址**才是决定速度的关键，
> 中枢内部「渲染口径」（jsm 里的网关地址）当前 `mode=direct` 下**不影响客户端速度**
> —— 下发的 jsm 里网关站点数为 0。

> ⚠️ **设备上开着梯子（VPN）时，局域网地址会取不到配置** —— 代理会把
> `10.0.0.11` 也送进隧道。关掉梯子，或把 `10.0.0.0/24` 加进直连/绕过列表。
> 详见 [常见问题](#八常见问题都是在真机上踩过的)。

> 相对路径（`./pg.jar`、`./lib/*.json`）会按配置地址自动解析，
> 所以用哪条地址都行，包内资源会自动从同一台服务器加载。

### 网盘 CK：一处保存，局域网多端自动生效（推荐）

> ⚠️ **本节所述的「中枢代管网盘 CK 多端同步」已于 2026-10-18 停用，代码保留但默认关闭。**
>
> 停用原因（四条硬约束，均已实测确认）：
> 1. 网盘 CK 实际由 App 主程序存储在端上（`TV/.<渠道>_user.pg`），PG 包只能**读**不能写；
> 2. 壳里注入的 JS **没有 `os` 模块也没有文件 IO**，无法把 CK 写回端上的 `.pg`；
> 3. 端对网盘 CK **只取不送** —— `PUT /hai/lib/tokenm.json` 实测恒为 0，
>    中枢拿不到任何凭据，「一处保存多端生效」在协议层就不成立；
> 4. 即便能拿到，中枢有值就会**覆盖端上刚扫码登录好的状态**，反而弄坏正在用的设备。
>
> **现在应该怎么做**：在 OK影视 App 里**扫码登录网盘**（各设备各自扫一次），
> CK 存在该设备自己的 `.pg` 里，只对该设备生效。
> 代理同理 —— 在 App 原版设置里填，不要指望中枢注入。
>
> 保险库相关代码（`core/ckvault.py` / `core/ckcheck.py`）**保留未删**，
> 开关 `OKTV_CK_SYNC=0`、`OKTV_DAV_REFILL=0`；关闭后 `tokenm.json` 渲染回原版模板，
> 字段零差异。想再启用时不必从头摸。

整包 79 个站点里 **59 个**的 `ext` 第一段都是 `./lib/tokenm.json` ——
夸克 / UC / 百度 / 115 / 迅雷 / 移动 / PikPak / 123 / 189 / 阿里 的 CK
全部由这**一个文件**承载。而 `./lib/...` 是相对「配置地址」解析的，
每台设备都会自己来中枢取这个文件。

所以中枢把 `tokenm.json` 做成了**动态渲染**：

```
GET /hai/lib/tokenm.json  →  模板（字段全集/默认值） + 保险库里的当前最优 CK
```

**在任意一台设备上存一次，全屋设备下次加载配置就自动生效**，不用每台重新扫码。

> ⚠️ 上面这句是**旧结论，已不成立**（2026-10-18 停用，实测端从不回写 CK）。
> 现在每台设备各自在 App 里扫码即可，中枢不参与。详见本节开头的停用说明。

#### 最省事的方式：让它自己回来（无感）

`csp_Config`（也就是 OK影视 里的「网盘及弹幕配置」源）的 `ext` 正是
`./lib/tokenm.json`。中枢下发的配置会把这个相对路径渲染成**该设备自己正在用的
绝对地址**：

```
device 请求 http://10.0.0.11:8099/hai/jsm.json
   → 配置里的 ext 变成 http://10.0.0.11:8099/hai/lib/tokenm.json
```

这样端对 tokenm.json 的**读和写都明确落在中枢 HTTP 上**，不再有「它以为是本地
文件、于是把扫码结果写进自己盘里」的歧义。写入端点接受**任何方法、任何形态**：

| 端怎么送 | 中枢怎么收 |
| --- | --- |
| `PUT/POST` 一整份 tokenm.json | 逐字段识别入库 |
| `POST` 表单 / multipart | 同上 |
| `GET …?quark_cookie=…` | 同上 |
| `Cookie` / `X-CK` / `Authorization` 头 | 同上 |

识别出的值立刻并入保险库，**其他设备下次加载配置即生效**。

> 这条通道是否真的被触发，取决于 PG 自己的实现。想确认的话打开
> **`http://10.0.0.11:8099/live`**（手机浏览器即可）—— 这张表每 3 秒刷新，
> 你一边在 OK影视 里做「网盘及弹幕配置 → 扫码/保存」，一边看请求有没有回来：
> 看到 `PUT`/`POST /hai/lib/tokenm.json` 就是通了；只有 `GET` 就说明 CK 还留在
> 设备自己身上，用下面的手动方式补一次即可。

#### 手动方式（三选一，都走同一个保险库）

| 方式 | 操作 |
| --- | --- |
| 手机/电脑浏览器 | 打开 `http://10.0.0.11:8099/ck`，粘贴 CK → 保存 |
| 管理页 | `http://10.0.0.11:8099/` → 「网盘 CK」面板 → 粘贴 → 保存 |
| 命令行 / 脚本 | `POST /api/ck/report`，见下方接口表 |

粘贴什么都能认：裸 Cookie 串、`quark_cookie=…`、`https://pan.quark.cn/…?cookie=…`、
整份 `tokenm.json` —— 自动识别是哪个网盘。

**覆盖规则**（对应「有效新 CK 自动覆盖旧 CK」）：

| 新值状态 | 行为 |
| --- | --- |
| 校验通过（valid） | **覆盖**旧值，旧值进 history（掩码保存，最多留 5 条） |
| 判不了（unverified） | 只填空位；已有有效值时不覆盖 |
| 明确失效（invalid） | **绝不覆盖**已有有效值；只记一条事件 |
| 播放成功 | 该渠道 `hits+1` 并自动置为有效 |

入库时会**真实调用网盘接口**校验登录态（夸克 / UC / 百度 / 115 / 123 / 189 / 阿里）。
迅雷 / PikPak / 移动 / 光雅需要客户端签名或验证码，服务端判不了，标 `待验证`——
**网络不通一律记 unverified，不会因为一次抖动把你的好 CK 清掉**。

**安全边界**：真实 CK **只回局域网来源**；公网来源（经 CF 隧道）只拿到空模板，
响应头 `X-CK-Scope` 会明确写 `lan` 还是 `public-masked`。
公网入口的 ingress 只放行 `/hai` 与 `/gw`，`/api/ck`、`/ck` 在公网是 404。
（想放开：`OKTV_CK_PUBLIC=1`。）

**自动嗅探**：任何带 CK 的请求经中枢且返回 2xx，会被自动识别入库并计一次播放命中
（`OKTV_CK_AUTOSNIFF=1`，默认开）。自己下发的 `tokenm.json` 与 `/api/ck*` 已豁免，不会自刷命中数。

> 首次用网盘内容时，播放器仍可能弹一次二维码 —— 那是客户端自己的登录态。
> 扫完把 CK 存进捕获台，之后所有设备都不用再扫。

## 二、它解决了什么问题

`pg` 这类包的抓取逻辑（`pg.jar`）本身没问题，坏的是**站点地址**：

| 站点 | 包内写死的地址 | 实际情况 |
| --- | --- | --- |
| 玩偶哥哥 | `wogg.888484.xyz` | 域名已废弃 → 现为 `woggpan.888484.xyz` / `www.wogg.live` |
| 木偶哥哥 | `123.666291.xyz` | 域名漂移 → `666.666291.xyz` 仍在，`muou.asia` 已是 DNSPod 停放页 |
| 蜡笔 | `xiaocgege.shop` | 已迁移到 `www.fmcf.fun` |
| 土豆 | `tudou.lvdoui.top` | 已跳转到 urldance 密码页（站点跑路） |

这些站用的是**同一套 jar 里的 CSP**，靠 `TAG` + 站点地址区分。
所以「换域名」是唯一有效修法 —— **改 jar 一点用都没有**。

本仓库把「**配置**」和「**地址**」彻底解耦：

```
公开社区配置 ──┐
              ├─→ 候选域名入池 → 健康巡检 → 选主 → 重新生成 jsm.json
站点名关键词 ──┤
历史域名知识库 ┘
```

## 三、健康巡检怎么判断「能用」

只按响应体大小判断会被骗 —— `muou.asia` 的 DNSPod **「域名已过期」停放页有 25KB**，
`urldance.com` 的**密码跳转页有 8KB**，都大于旧的 20KB 阈值。

所以改成**内容特征双判**：

| 判据 | 结果 |
| --- | --- |
| HTTP ≥ 400 / DNS 失败 / 连接超时 / SSL 异常（**已重试 3 次**） | `dead` |
| 命中「域名已过期 / 请输入密码 / dnspod / urldance …」**且**无站点特征 | `dead` |
| 命中 **CF/WAF 人机校验页**（Attention Required / 浏览器安全验证 …） | **q1「存活但存疑」**，不判死 |
| 带站点特征（`/vod` `/type/` `/search` `api.php` …）且 ≥ 100KB | **q3 完整真站** |
| 带站点特征 | **q2 真站** |
| **网盘聚合类**（SPA 首页，无 `/vod` 特征）但像前端应用 | **q2 真站**（≥1.5KB）/ q1 空壳（≥0.5KB） |
| 存活但无站点特征（门户页） | q1 兜底，**不会被用来替换原地址** |

选主顺序：`q3 → q2 → q1`，同级看延迟。

**判「失效 / 告警」的口径与「替换原地址」不同**：

* 替换地址只认 `q≥2`（质量不足宁可不用）；
* 判失效只要求 `q≥1` —— 只要站点还有响应就不打扰用户。**要求「一个响应的都没有」**
  才算失效，且要连续 `OKTV_OFFLINE_CONFIRM`（默认 2）轮。

### 为什么口径要这么细（三件真事）

1. **瞬时失败 ≠ 永久失效**：`fmcf.fun`（蜡笔）一次 `ConnectionError` 被判死，
   手工一访问却是 **200 + 623KB** 的真站。所以异常类失败要重试。
2. **网盘聚合站的首页本来就不像影视站**：`jying.top`（聚影）是 3.6KB 的 Vue 首页，
   没有 `/vod`，被「无站点特征」误杀。
3. **CF 拦的是我们的 IP，不是站点死了**：`hdhaven.com` / `re0.me` / 观影的域名
   在服务器上全是 403 或「浏览器安全验证」，但**家庭宽带能正常用**。
   把挑战页和停放页混在一档，等于拿探测机的网络环境去判用户的可用性。

修完这三条重跑巡检，**9 个 TAG 一次性恢复**（`LABI`/`HUAMUCANG`/`GUANYING`/
`PANLIAN`/`HDHIVE`/`hdhaven`/`csp_XiaoZhang`/`csp_Meijumi`/`csp_PikaSo`），
域名池存活 20 → 28。

> 顺带一个决定：**不再往站点名里写 `⚠️失效`**。除了破坏与原版逐字一致，
> 端还会缓存配置，等站点恢复了中枢已去掉标注、端上那份还是旧的，又变成
> 「恢复了标注还在」。失效状态只在 `GET /api/sites`、`/live` 和私聊告警里体现。

## 四、自动化维护

服务器上跑着一个中枢（`tools/` 里是它的全部源码）：

| 能力 | 说明 |
| --- | --- |
| 定时巡检 | 每 10 分钟探一次域名池（**串行二审**，避免并发把出口挤爆造成假失效） |
| 上游同步 | 每 6 小时拉 16 个公开社区配置 + 采集域名；含**饭太硬导航变动监视** |
| **每日巡检** | 每天 08:00 跑一次完整「同步 → 巡检 → 重生成」，并私聊管理员 |
| 失效告警 | 某接口由「有可用」变「无可用」时立即通知 |
| 恢复通知 | 失效接口重新拿到可用地址时通知 |
| 网关反代 | `/gw/<TAG>/…` 实时转发到当前最优域名，配置写死也不会随域名漂移失效 |
| **入口测速** | 每小时测各对外入口的 jsm 耗时与 pg.jar 带宽（`core/epbench.py`） |
| **渲染口径择优** | 可选「最快优先 / 仅故障切换」自动挑入口（`core/renderbase.py`，默认关） |
| **PG 包自动更新** | TG 群 / TG 手动转发 / 网页上传触发，八步流水线 + **失败自动回滚** |
| **上游变动告警** | 监控饭太硬导航里各站源的新增 / 消失 / 换域名 / 路径变化 |
| **新站源一键加入** | 维护页「上游新站源」列表每条带「加入」按钮，过**三道闸**后写进 PG 包配置 |

### QQ 命令（SEA 机器人插件）

插件在 `plugin/hai-package/index.js`，装到 SEA2 的 `plugins/` 目录即可。

| 命令 | 效果 |
| --- | --- |
| `修复接口` | 立即触发一次「同步 → 全池巡检 → 重生成 hai 包」（约 1~3 分钟，**分阶段回报进度**） |
| `接口状态` | 汇总：**正常接口清单**（一行列出全部名字）+ 各状态数量 + 域名池存活 + 上次巡检时间 + **全部入口地址**（局域网 / 多条公网 / WebDAV）+ 失效/存疑清单（带中文名） |
| `接口明细` | 逐条列出**有远程域名的接口**（带序号、中文名、状态、域名、延迟）；55 个内置接口（本地脚本/jar/分享库）压成末尾一段紧凑清单 |
| `接口明细 玩偶` | **按关键词只列匹配的接口** —— 名字 / key / TAG / api / 域名都能匹配（别名 `查接口`、`接口详情`） |
| `hai帮助` | 命令列表 |

权限级别 2（超管），有 60 秒防连点，**支持带 `@机器人` 前缀**。

状态图标：`✅` 正常 · `🛡` 存疑（被 WAF/人机校验拦，不判失效） · `👀` 观察中 ·
`⚠️` 已确认失效 · `❓` 未纳入巡检 · `📦` 内置接口（ext 里没有远程域名）。

> 明细里的域名是**配置里实际生效的那一个**：原地址还活着就显示原地址（不换），
> 只有原地址失效才会显示替换后的新域名 —— 与下发配置始终一致。

> 明细**必须显示中文名**：原包站点名是 `玩偶哥哥|网盘`、`木偶哥哥|网盘`，
> 英文 key 却是 `Wogg` / `Mogg`。只列 key 会让人以为这些接口不在列表里
> （用户就反馈过「怎么没有玩偶哥哥和木偶那些接口」）。现在显示为
> `✅ 玩偶哥哥|网盘（Wogg） · woggpan.888484.xyz 1711ms`。

### 交互约定：绝不静默

三条约定，任何一条断了都会表现成「发了命令毫无反应」：

1. **收到即有回执** —— 先回 `⏳ 收到「xxx」…` 再取数据；长任务回执后转后台跟踪，
   不阻塞消息分发链。
2. **长任务分阶段回报** —— 按 `① 上游同步 → ② 全池巡检 → ③ 重新生成` 逐步回报，
   每步带结果与累计用时。判据是「该步的成果数据是否已出现」而非当前阶段名，
   所以轮询跨过某个阶段也不会漏报。
3. **失败一定说出来** —— 中枢不可达 / 返回异常 / 进程异常都有明确提示，
   附中枢地址与排查命令；权限不足也会回复。

### 部署（容易漏的一步）

插件与中枢是两个独立目录，**改完插件不部署等于没改**。已并进主流程：

```bash
python deploy/deploy.py --no-assets     # 中枢 + 插件 + 框架检查 + 重启 sea2-bot
python deploy/deploy.py --no-plugin     # 只更新中枢
python deploy/deploy.py --no-restart    # 更新插件但不重启
```

### SEA 框架补丁（`tools/deploy/sea/base-adapter.js`）

`sea1`/`sea2` 的 `adapters/base-adapter.js` 原本只写 `context.permissionLevel`，
而 `core/plugin-manager.js` 读的是 `context.userPermission` —— 后者恒为 `0`，
凡 `permissionLevel > 0` 的插件都会在分发层被 `continue` **静默跳过**，连
「权限不足」都发不出来。补丁让两个字段名并存，部署脚本**检查后再补**（已修复则跳过，
不覆盖人工改动），原文件备份在 `/root/sea{1,2}/backups/`。

## 五、自己部署一份

```bash
# 目标机：Debian 10+ / Python 3.8+
python3 -m venv /opt/oktv-hub/.venv
/opt/oktv-hub/.venv/bin/pip install flask requests
cp tools/deploy/oktv-hub.service /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now oktv-hub
```

## 六、入口测速与渲染口径（2026-10-23 新增）

中枢对外有**多条入口**（局域网直连 / Cloudflare / gost）。两条维护动作：

**① 测速（`core/epbench.py`）** —— 每条入口测两项：

| 探针 | 测什么 | 失败含义 |
| --- | --- | --- |
| `jsm.json` 往返 | 客户端拉配置的实际耗时 | 这条入口**不可用** |
| `pg.jar` Range 拉 1MB | 下载带宽 | **只是测不出带宽**，不代表入口不可用 |

两条探针的成败**严格分开** —— 早期版本把「带宽测超时」混进「入口不可用」，
结果 gost 隧道抖动一次就被误判成死链。

判定也改了：**要求全部轮次都失败**才算不可用。gost 隧道实测会抖
（同一 URL 连打 8 次偶发 404 / 连接断开；耗时在 1.4～4.3 s 之间乱跳），
单次失败就判死会误触发故障切换。

**② 渲染口径（`core/renderbase.py`）** —— 决定下发的 jsm 里网关地址用哪条入口。
三档可选：

| 档 | 行为 |
| --- | --- |
| `0` | 关闭自动择优（默认） |
| `1` | 仅故障切换 —— 当前口径连续 3 轮不通才切走 |
| `2` | 最快优先（含滞回，避免来回抖） |

所有原本读 `C.PUBLIC_BASE` 的代码路径（`patch.gateway_base` / `report.public_bases` /
`endpoints` / `app` / `ckvault` / `gateway`）统一改读 `renderbase.current()`。

> **当前 `mode=direct` ⇒ 渲染口径对客户端速度零影响**：下发 jsm 里 `_GW` 网关站点数为 0，
> `/gw/` 串命中 0 条；`PUBLIC_BASE` 只在 gateway/dual 模式才写进配置。
> 真正影响电视拉取速度的是**电视里填的那个配置地址**。

**手动指定**：维护页「配置地址」卡片里，每个测速通过的入口都有「设为口径」按钮，
也可以在「渲染口径」面板里选档位或「交回默认」。

## 六点五、接口顺序、显隐与签到 CK（2026-10-23 新增）

### 接口顺序与显隐（`core/siteorder.py`）

客户端「接口选择」页里接口的**顺序 = 下发 jsm 里 `sites` 数组的顺序**。
维护页「接口明细」卡片提供直接编辑：

| 操作 | 说明 |
| --- | --- |
| ↑ / ↓ | 上移 / 下移一条，立刻 `do_render()` 重生成下发配置 |
| 🚫 隐藏 | 该接口**不下发**，客户端「接口选择」里不出现（维护页仍可见、仍可恢复） |
| 恢复自动排序 | 交回自动排序（置顶 → Wogg/Mogg → 最快存活延迟升序 → `*_GW` 末位） |
| ↶ 撤销上次重置 | 撤销上一次「全部重置」（重置前自动压快照） |
| 全部恢复显示 | 把隐藏的接口全部放出来 |

**顺序与显隐都持久化**在 `data/site_order.json`，**换 PG 包后保持不变**
（`data/` 不在镜像范围内）。手排之后延迟自动排序不再接管 —— 用户意志优先。

> **隐藏的语义要说清**：隐藏 = 不下发，所以 `verify` 的 `sites.missing_keys` 会非空。
> 豁免**只对隐藏名单生效**（`sites.hidden_keys`），名单外的缺失照旧报错 ——
> 「不精简原版」这条红线没有放宽。隐藏项仍保留在 `baseline` 与维护页里，
> 随时可以恢复显示。

> **改了顺序电视上没变？** —— 那不是没生效，是**端没重新拉配置**。
> FongMi 壳的 `BaseConfig.ensureLoaded()` 进程内已加载就直接 return，
> 所以必须**彻底退出 App 重开**，或在「设置 → 点播 → 选中本配置 → 确定」重新选一次。
> 维护页「客户端拉取」卡片会显示**设备最后一次拉取 `jsm.json` 的时间 / IP / UA**，据此判断。

### 签到 CK（`core/checkin_ck.py`）

维护页「签到 CK · 提交与体检」卡片，管的是**一条龙签到**项目
（`/opt/dailycheckin/config/config.json`）的站点凭据，**与网盘 CK 是两回事**：

- 10 个站点（TIEBA / SMZDM / ALIYUN / BILIBILI / YOUDAO / KGQQ / V2EX / ACFUN / IQIYI / BAIDU）
- 每站一行：状态灯 + 脱敏预览 + 「↗登录」直达登录页 + 输入框 + 保存
- 顶部「◎ 检测全部 CK」，保存后自动单站校验
- 三态哲学：valid（明确登录成功）/ invalid（明确失效）/ **unverified**（接口不通或校验方式未知，**不误判成失效**）
- 保存即写 `config.json`，次日 08:30 的定时任务用新 CK 签到

> ⚠️ 这个卡片**必须留在源码树里**（`core/checkin_ck.py` + `app.py` + `web/live.html`）。
> 中枢每次部署都整体覆盖 `app.py` 与 `live.html` —— 只改服务器文件的话，
> 下一次部署就没了（2026-10-23 已踩过一次）。

## 六点六、上游新站源「一键加入」PG 包（2026-10-23 新增）

维护页「上游里的新站源（PG 没有的）」列表，**每条后面都有一个「加入」按钮** ——
点一下就把那个站源写进 PG 包配置，端上「接口选择」页就能看到它。

### 三道闸

| 闸 | 检查什么 | 不过会怎样 |
| --- | --- | --- |
| ① 能力闸 | `csp_XXX` 的解析类在**本包 `pg.jar`** 里存在吗？`ext` 引用的文件在包里吗？ | 直接拒：「本包 jar 里没有 csp_XXX 这个解析类」 |
| ② 探测闸 | 真连一次接口，HTTP 有没有响应 | 拒，但提示「仍要强行加入吗」（用户可坚持） |
| ③ 落盘闸 | 写进 `data/added_sites.json`，由 `patch.build()` 注入 | 任一步失败自动回滚，配置保持原样 |

### 为什么必须有第一道闸（实测数据）

上游 16 个源登记出 **307 个**新站源，去重后 217 个不同的 `csp_` 解析类，
**只有 20 个**在本包 `pg.jar` 里（线上 jar 共 454 个 spider 类）。
也就是说 **90% 的站源就算域名活着，加进来也是空壳** —— 端上一打开就报
「解析器不存在」。所以静态判定必须放在**加入之前**，而不是加完再看端上报错。

> `csp_XXX` → `com.github.catvod.spider.XXX` 是 TVBox 的固定映射。
> `pg.jar` 只含 `classes.dex`（没有 `.class`），用正则从 dex 里抓类型描述符即可，
> 不必反编译 —— 一次全扫 11MB dex 约 1~2 秒，按 `mtime:size` 指纹缓存到
> `data/jar_index.json`。

### 独立 TAG，不与原版共用

新增站点一律用 `ADD_<md5前8位>` 作 TAG。原因：上游常见**多个不同站点共用一个解析类**
（`csp_TTian` 同时是「追剧」和「天天」，`csp_BiliGuard` 同时是「少儿教育/小学课堂/初中课堂」）。
按 `api` 归 TAG 会让 A 站的地址被 B 站的域名顶掉。独立 TAG 之后实测：

```
追剧 → ADD_5b23de3d (app.kzjtv.com)
天天 → ADD_eafa867f (op.ysdqjs.cn)     ← 互不干扰
```

### 三条判定路径必须口径一致

`/api/newsite`（清单）、`/api/newsite/probe`（探测）、`/api/newsite/add`（加入）
三处都要判重 + 判能力，用的是同一套 `addsite.dup_check()` / `addsite.static_check()`。
踩过的坑：

- 清单按 key 单键索引 → 同一个 key 在 4 个上游源里 api 不同时会**张冠李戴**，
  拿 A 源的 api 配 B 源的 ext，判定全错。**必须按源隔离 + key+api 配对**。
- `probe` 路由漏了判重 → 清单说「重复」，probe 说「可以加」，用户点下去被拒。
- `libfill` 派生文件（`tokenm.json` ← `tokentemplate.json`）本地没有磁盘文件，
  但线上一定有 —— 判定要认这条派生关系，否则本地比线上严，两边结论对不上。

### 不破红线

`core_ok` 的六条判定里**不含 `added_keys`** ⇒ 新增站点不破坏红线（实测
`added_keys=['Wo4k']` 时 `core_ok=True`）。但**新增文件会破**
（`unexpected_extra` 非空），所以加入只改配置内容，不往包里塞文件。

### 加入后端上要做什么

端**只在 App 进程启动时拉一次 `jsm.json`** ⇒ 调完顺序/加入新站后，
必须**彻底退出 App 再打开**才会看到。

### 移除要连域名池一起清

TAG 是按 key 算的，站点移出 `added_sites.json` 后就查不到 key → TAG 的对应关系。
所以 `remove()` 会**先把 TAG 返回出来**，调用方拿它清域名池；另有
`prune_orphan_pool()` 在启动时清理历史残留。

> 中枢每次部署都会整体覆盖这两个文件 —— 任何只改服务器、不进源码树的页面改动，
> 下一次部署就会被冲掉（2026-10-23 已因此丢过一次「签到 CK 上传卡片」，
> 现已把该功能合进 `core/checkin_ck.py` + `app.py` + `web/live.html` 根治）。

## 八、常见问题（都是在真机上踩过的）

### 1. `配置获取失败` —— 十有八九是手机/电视上开着梯子

**症状**：同一个 `http://10.0.0.11:8099/hai/jsm.json`，
电脑浏览器能打开，手机/电视上的播放器却说「配置获取失败」。

**根因**：设备上开了 VPN / 代理（梯子），
**`10.0.0.11` 这类局域网地址也被塞进了代理隧道**，
而梯子的服务端当然回不到你家内网 → 请求直接死掉。

**处理**（任选其一）：

| 做法 | 说明 |
| --- | --- |
| 关掉梯子 | 最干脆，局域网本来就不需要走代理 |
| 把 `10.0.0.0/24` 加进**绕过/直连列表** | Clash 用 `Bypass` / 分流规则；Surge/V2Ray 用 `bypass` / `direct` |
| 改用公网地址 | `https://hai.haihaigege.dpdns.org/hai/jsm.json`（走梯子也没问题） |

### 2. 公网地址能用但很慢 / 反复重试

`pg.jar` 有 **4.5MB**，走公网 = 走家里宽带上行 + CF 隧道。
实测同一个文件三次：2.1MB 超时 / SSL 失败 / 4.6MB 成功（14.6s）。
**能走局域网就一直走局域网**（实测 0.02s）。

### 3. 想让服务端能诊断「客户端到底连没连上」

中枢会把每个请求记进 `logs/access.jsonl`（含来源 IP、UA、Range、Connection）：

```bash
curl -s http://10.0.0.11:8099/api/access | python3 -m json.tool | tail -40
```

播放器报错时先看这里：
- **完全没有该设备的记录** → 客户端根本没连上（网络/代理问题，见第 1 条）
- **有记录但 4xx/5xx** → 服务端问题
- **有记录且 200** → 配置没问题，去查播放器侧（缓存、版本、spider）

### 4. 我在手机上扫码设了网盘 CK，为什么别的设备还是让我扫码？

> ⚠️ **本节（含下面两个通道）记录的是已停用的旧方案**（2026-10-18 停用）。
> 现在的答案很简单：**这是设计如此** —— 每台设备各自在 App 里扫码，
> CK 只存在该设备自己身上，不经过中枢，也不需要中枢。
> 本节保留供复盘与日后重启该方向时参考。

先说清楚一件事：**扫码这个动作本身不经过中枢**。它的流程是
「OK影视 打开「网盘及弹幕配置」→ 显示二维码 → 你去网盘 App 授权 → 凭据落到
**那台设备自己身上**」。同理，播放网盘内容时网盘 API 也是**直连**
（`pan.quark.cn` / `drive.uc.cn` …），同样不经过中枢。

所以中枢能自动拿到的，只有「设备主动把凭据送回来」的那些请求。

**怎么确认**：打开 **`http://10.0.0.11:8099/live`**，
先点一下表头的 **「🧹 清零基线」**（把旧的观测数据清掉，`/api/probe/reset`），
然后在 OK影视 里做一次「网盘及弹幕配置 → 保存 / 重新扫码」，盯着那张表：

| 你看到的 | 含义 | 怎么办 |
| --- | --- | --- |
| `PUT`/`POST /hai/lib/tokenm.json` | 端确实把凭据送回来了 | 已自动入库（**注意：端实测从不这样做**） |
| 只有 `GET /hai/lib/tokenm.json` | 端只是在**取**配置，没往**写** | ⛔ 这就是实际常态。**在 App 里各自扫码** |
| 连 `GET` 都没有 | 那台设备压根没连中枢 | 见上面第 1 条（多半是梯子） |

> ⚠️ 本节是**旧方案的排查记录**，保留供复盘。现行做法：每台设备在 OK影视 App 里
> 扫码登录网盘，CK 存在该设备自己的 `TV/.<渠道>_user.pg`，只对该设备生效。
> `/api/devices` / `/api/probe` 现在只作**只读观测**用。

`/api/devices` 里 `ck_in > 0` 的设备就是贡献过 CK 的；`/api/probe` 保留原始报文
（方法 / query / body 片段 / 关键头），排查时不用再猜。

#### 已实测确认：端不会回写

真机抓到的访问记录（`10.0.0.108`，UA `okhttp/5.0.0-alpha.14` 就是 OK影视 壳）：

```
01:01:12  GET /lib/tokenm.json  200  len=2975
01:01:27  GET /lib/tokenm.json  200  len=2975
01:01:55  GET /lib/tokenm.json  200  len=2975
```

**每 15~30 秒拉一次，清一色 GET，零 PUT/POST。** 所以「等它自己写回来」这条路
不成立，得主动把它的**外发**请求引到中枢。为此做了两条通道：

#### 先搞清一件事：端上的 CK 就是一个明文文件

每个渠道的凭据都落在 App 自己的配置目录里，**一个渠道一个文件**：

```
/storage/emulated/0/TV/.quark_user.pg        ← 夸克
/storage/emulated/0/TV/.baidu_user.pg        ← 百度
/storage/emulated/0/TV/.<渠道>_user.pg       ← 其余同理
```

App 的「查看凭据」会直接把这个路径显示给你。该目录属**外置存储、非私有目录** ——
电视上装个文件管理器、打开「显示隐藏文件」，就能看 / 拷走 / 删掉 / 替换。
**所以「同步 CK」本质就是「同步这些文件」。**

WebDAV 这边的文件名与它**去掉 `_user.pg`、换成 `.json`** 一一对应：

| 端上的落盘文件 | WebDAV 名 | 渠道 |
| --- | --- | --- |
| `.quark_user.pg` | `quark.json` | 夸克 |
| `.uc_user.pg` | `uc.json` | UC |
| `.baidu_user.pg` | `baidu.json` | 百度 |
| `.115_user.pg` | `115.json` | 115 |
| — | `aliyun / 123 / 123_open / 189 / thunder / pikpak / youtube / bili / hdhive / hdhaven / ysp_uid / fylive_ua / playprogress.json` | 阿里云盘 / 123 / 天翼 / 迅雷 / PikPak / YouTube / B站 / 影巢 / 栖影 / 弹幕 / 直播 / 进度 |
| — | `cookie_<站点key小写>.json` | PG 站点 Cookie（`cookie_guanying` / `cookie_panta` / `cookie_panlian` / `cookie_qwmp4` / `cookie_woniu` / `cookie_4kzn` / `cookie_huamucang`） |

端 PUT 上来的封装格式（实测样本）：
`{"cookie":"<裸 cookie>","_last_modified":<epoch秒>,"sitename":"<NAME>"}`

#### 通道一：WebDAV 缓存（推荐先试这个）

把「网盘及弹幕配置」里 **WEBDAV 缓存网盘信息** 的地址填成：

```
http://10.0.0.11:8099/gw/dav
```

账号 / 密码**随便填**（中枢不校验，只按来源网段放行）。这条链路是**双向**的：

| 方向 | 什么时候发生 | 效果 |
| --- | --- | --- |
| **上行**（端 → 中枢） | 端**本地登录态发生变化**时才 PUT（单纯「填地址」只会 GET + 写一个 `connection_test.json`） | 凭据自动入库 → 其余设备下一轮拉配置就生效 |
| **下行**（中枢 → 端） | 端**约每 30 分钟**来取一批，另外**打开对应网盘设置时会立刻取** | **往保险库写一次 CK，端下次来取就自动写进它自己的 `.pg` 文件 —— 不用扫码、不用在电视上点任何东西** |

下行这条叫 **「回填」**：端来要 `<渠道>.json` 而中枢手上没有落盘文件时，用**保险库当前
最优 CK** 按上面的封装格式合成一份给它。目前开通回填的是格式已实测确认的四个 cookie 类渠道
（**quark / uc / baidu / 115**）；账号密码类（thunder / pikpak / pan123 / pan189）与 token 类
（aliyun / yd / guangya）的确切字段名还没实测到，**宁可不合成也不猜**（猜错会把端上那份还能用的
凭据顶掉）。用 `OKTV_DAV_REFILL=0` 可整体关闭。

回 `/live` 看 **WebDAV 端点** 面板：会有「🔁 回填就绪 N 个」一行，逐条列出
`<渠道>.json → /storage/emulated/0/TV/.<渠道>_user.pg`。

| 你看到的 | 含义 |
| --- | --- |
| 出现 `PUT` | ✅ 端把凭据送上来了，已自动入库，别的设备恢复即可 |
| 只有 `PROPFIND` / `GET` | 端连上了但本地凭据没变化过，所以不会 PUT |
| 什么都没有 | 端没用这个地址，或那台设备没连中枢 |

> **更正一条旧说法**：早先「WebDAV 只能同步影巢 / 栖影 / 123开放 / 光雅 / YouTube / B站、
> 夸克百度不在内」是**错的** —— 那是照 `pg.jar` 里的类名推的，而 `pg.jar` 全文搜
> `webdav` / `quark` 命中都是 **0**：这套同步是 **OK影视 App 主程序**的功能，不在 PG 包里。
> 实测端同步的清单见上表，**夸克 / 百度 / UC / 115 / 123 / 189 / 迅雷 / PikPak 本来就在内**。
> 另外：App 设置里的「备份与恢复」备的是**本地数据库**（历史/收藏），与 WebDAV 无关。

#### 通道二：外部中转（阿里云盘）

`tokenm.json` 里 `open_api_url` 指向「网盘换 token 的接口」，端扫码/刷新后的凭据
会 POST 到那里 —— 本来直连第三方，中枢看不见。`/live` 上一键开启
**「地址改写」**后，该地址指向 `http://10.0.0.11:8099/gw/ali/token`：
**原样透传上游**（端功能不受影响），同时把凭据截下来入库。

开启后让端重新扫码一次（或重启 App 触发一次 token 刷新），再看 `/live` 的
**外部中转**表有没有请求进来。

> 已实测：中转链路本身完全正常（透传 + 截留 + 落盘都验证过）。
> 关于 `api.extscreen.com`：先前「整站 404」的说法要修正 —— 那个 404 是对
> **根路径 `/`** 的响应；`/aliyundrive/token` 返回的是 **403 + 10.6KB 自定义
> 错误页**（蓝色 `#39f` 模板，不是 Cloudflare），说明接口存在、只是拒绝了假
> token。但它**按 UA 分流**：换 `okhttp/5.0.0-alpha.14` 请求会变成
> `404 page not found` —— 即 **原包里这个换 token 的地址已经和上游对不上**。
> 这不是中转改坏的（改写关着时端也走这个地址），所以改写暂时保持关闭。

### 5. 接口被标了「失效」，但我在软件里能用？

**这是我们的判定错了，已修**（2026-10-15）。三条根因：

1. **瞬时失败被当成永久失效** —— `fmcf.fun`（蜡笔）一次 `ConnectionError` 就判死，
   手工一访问却是 200 + 623KB 的真站。现在异常类失败会**重试 3 次**。
2. **网盘聚合站的首页没有 `/vod` 特征** —— `jying.top`（聚影）是 3.6KB 的 Vue 首页，
   被「无站点特征」误杀。现在按接口名识别出网盘类并放宽判定。
3. **Cloudflare 拦的是探测机的 IP，不是站点死了** —— `hdhaven.com`、`re0.me`、
   观影的域名在服务器上全是 403 / 「浏览器安全验证」，但**家庭宽带能正常用**。
   这类页面现在判为「🛡 存疑」，**不替换地址、不判失效、不告警**。

修完重跑巡检，9 个 TAG 一次性恢复。

另外**不再往站点名里写 `⚠️失效`**：端会缓存配置，等站点恢复了中枢已去掉标注、
端上那份还是旧的 —— 那才是「恢复了标注还在」的来源。现在失效状态只看
`接口状态` / `接口明细` 命令或 `/api/sites`。

## 九、与本仓库的边界：哪些是本仓库做的，哪些不是

### 9.1 讲清楚「会不会被精简」

**不会。** 本仓库对 pg 包只做一件事：**把失效站点的域名换成当前可用的域名**。

配置里其它一切——**特别是直播源 `lives`**——都原样保留，一个字节都不改。
资源文件（`pg.jar`、`js/`、`lib/`）也原样保留，实测 **87 个原版文件 sha256 全部一致**。

**随时自查**（管理页有「🛡 与原版比对」按钮，或直接调接口）：

```bash
curl -s "http://10.0.0.11:8099/oktv/api/verify?deep=1" | python3 -m json.tool
```

```jsonc
{
  "core_ok": true,
  "verdict": "与原版逐项一致（仅按需替换了失效域名）",
  "fields": {                        // 逐条指纹比对，same=true 表示一条不差
    "lives":  {"original": 36, "now": 36, "same": true},
    "rules":  {"original": 17, "now": 17, "same": true},
    "proxy":  {"original": 14, "now": 14, "same": true},
    "hosts":  {"original":  5, "now":  5, "same": true},
    "doh":    {"original":  5, "now":  5, "same": true},
    "flags":  {"original": 10, "now": 10, "same": true}
  },
  "scalars": { "spider": {"same": true}, "wallpaper": {"same": true}, "...": {} },
  "sites":   { "original": 79, "now": 68, "missing_keys": [], "api_changed": [], "type_changed": [],
               "hidden_keys": ["…"] },   // now=68 是因为 11 个被用户在维护页手动隐藏
  "domain_rewritten": [ /* 预期内的修复，通常 3 条 */ ],
  "files":   { "original": 87, "missing": [], "size_diff": [], "hash_diff": [], "unexpected_extra": [] }
}
```

> **关于 `now: 68`**（2026-10-23）：维护页允许把接口**隐藏**（不下发给客户端，
> 客户端「接口选择」页里不出现）。当前有 11 个处于隐藏态，所以 `now` 比 `original` 少。
> 隐藏名单会原样出现在 `sites.hidden_keys` 里 —— `missing_keys` 为空即代表
> **除隐藏项外一条不缺**。隐藏项仍保留在 `baseline` 与维护页里，随时可以恢复显示。
>
> `files.unexpected_extra` 也是红线之一：**新增文件视为破**（原版没有的东西不能凭空出现）。
> 豁免名单仅限 `jsm.json` / `VERSION` / `README.txt` 与 `lib/{tokenm,webdav,alistjar}.json`、
> `sambashare.txt`。

### 9.2 直播为什么可能「看起来少了」——这不是精简，是运行位置的问题

`lives` 里 36 个直播分组，**29 个的地址是 `http://127.0.0.1:10079/…` 和 `http://127.0.0.1:35456/…`**：

| 端口 | 作用 |
| --- | --- |
| `10079` | 直播 m3u 聚合 + 代理转码（`/c/3600/null/<url>`、`/mp4/3600/null/<url>`） |
| `35456` | 源服务（`/tv.m3u`、`/migu.m3u`、`/bililive.m3u`、`/proxym3u/` …） |
| `10077` / `10078` | 代理 / YT 解密增强 |
| `19090` / `7777` / `10172` | 代理 / 版本 / 其它 |

**`127.0.0.1` 指的是播放设备自己**，这些服务由 `pg.jar` 与播放壳在设备端启动。
另外 4 条是外网直连（`aktv.top`、`tv.iill.top`、`sub.ottiptv.cc`），2 条读本地文件
（`./lib/biptv.txt`、`./lib/ytblive.m3u`，其中 `ytblive.m3u` 原版发行版里本就不存在）。

所以：**只要 `pg.jar` 在设备上正常加载，这些直播源就和原版一模一样**。
如果直播列表明显变少，按下面顺序查：

1. **清播放壳缓存 + 强杀重开**（作者 README「提示1」原话：影视壳有时加载不了最新的 jar）
2. **确认壳是 OK影视 / 影视**（作者原话：其他播放器或魔改壳用这个 zip 会导致网盘内容无法播放）
3. **看访问日志确认壳有没有取到包**：`/api/access`
   - 完全没记录 → 客户端没连上（先查代理/梯子）
   - 有 `jsm.json` 200 但没有 `pg.jar` → 壳在用本地缓存的 jar，清缓存后重试
4. 手机端和电视端分别试一次，排除单端壳版本差异

### 9.3 lib 资源的处理方式

上游发行版里有两类「缺文件」，处理方式不同：

| 文件 | 原版状态 | 本仓库 |
| --- | --- | --- |
| `tokenm.json`、`sambashare.txt`、`webdav.json`、`alistjar.json` | 只给模板/示例，**要使用者自己复制改名**（作者 README 明确写了步骤） | **代为生成**（从模板派生，等价于替使用者执行 README 的步骤）；`tokenm.json` 另外叠上网盘 CK 保险库 → 见第一节 |
| `4kzn.txt`、`guanying.txt`、`hdhaven.txt`、`hdhive.txt`、`huamucang.txt`、`panta.txt`、`qianfan.txt`、`woniu.txt`、`yiso.txt`、`ytblive.m3u` | **本来就不存在**（404），由 jar 自己向站点拉 | **保持不存在**，与原版一致 |

> `tokenm.json` 的**字段全集永远取自原版模板**，只覆盖 CK 那几个字段；
> 其余字段（各网盘的线程数 / flags / 代理 / pan_order）原样保留，`/api/verify` 已确认这一点。

> 早期版本曾为后一类落「空文件占位」，已撤销。原因：这些是 jar 向站点拉取的**本地缓存清单**，
> 给空文件等于告诉 jar「本地清单就是空的」，反而会让内容变少；404 时 jar 会走自己的回退逻辑。

实测不生成第一类的后果：播放器会在 2 秒内对 `/hai/lib/tokenm.json` 重试 16 次，拖慢配置加载。

- 部分站点（土豆、盘链、盘Ta、至臻、栖影、大盘搜、88网盘、校长影视、聚影、观影）
  **从国内家宽已不可达**：DNS 废弃、502、Cloudflare 403 或跳转密码页。
  这类站点没有「正确域名」可换，接口会被标注 `⚠️失效`，等上游复活后自动恢复。
  **注意：只改站点的显示名和 ext 里的域名，不删除站点**，所以列表长度和原版一致。
- 域名池只收**公网地址**：上游配置里大量 `http://127.0.0.1/…` 占位符必须过滤，
  否则播放器会去连自己。
